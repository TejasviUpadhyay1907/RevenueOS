# RevenueOS Phase 2B — Production-Grade Decision Intelligence

## Current Architecture (as of Phase 2A)

- **Backend**: FastAPI with API v1 endpoints.
- **ML**: A LogisticRegression model trained on `would_recover_with_action_B` (payment-link) using context features only.
- **Opportunity Engine**: Computes expected value = amount * recovery_probability * intervention_success_probability (fixed 0.8).
- **AI Planner**: Rule-based action selector (notification, smart_retry, payment_link) based on probability thresholds.
- **Policy Engine**: Simple amount limit (₹10,000) check; now upgraded in Phase 2A to include retry limits, contact limits, dispute/opt-out stops, human-approval threshold.
- **Execution Layer**: Delegates to a counter‑factual simulator that returns outcomes based on hidden ground truth, with idempotency via action_id.
- **Verification Layer**: Returns simulator outcome (trusted in synthetic world).
- **Database**: SQLAlchemy models for merchants, customers, payments, revenue_events, recovery_opportunitions, recovery_decisions, recovery_actions, policies, audit_events (audit_events now being used).
- **Synthetic Data**: Generated by `simulator/generate_dataset.py` with per‑action counter‑factual outcomes (would_recover, recovered_amount, time_to_recovery_hours, attempts_required, customer_contacts, action_cost) for actions: NO_ACTION, IMMEDIATE_RETRY, DELAYED_RETRY, PAYMENT_LINK, NOTIFICATION, HUMAN_ESCALATION.
- **Experiment Framework**: `backend/app/experimentation/` with baseline (fixed‑retry), simulator, metrics, reports, runner. Uses temporal split (60/20/20) and holds out test set for final evaluation.
- **Frontend**: Basic Next.js home page showing metrics; no decision trace or experiment UI yet.
- **Tests**: Unit tests for counter‑factual generation, information boundary, baseline, simulator, policy, experiment runner; plus existing API health/root tests.

## Current Data Flow (Experiment)

1. Load held‑out test set (events after temporal split).
2. For each event, build a `DecisionContext` (observable data only).
3. **Baseline Strategy**: deterministic fixed‑retry logic → selects action (IMMEDIATE_RETRY or NO_ACTION based on retry count).
4. **RevenueOS Strategy** (current Phase 2A greedy): computes expected recovered = amount * P(recovery | context, action) using a model that gives probability for PAYMENT_LINK (from LogisticRegression) and heuristic for other actions; selects the permitted action with highest expected recovered.
5. Selected action + event_id sent to **Executor** → calls **Simulator** which looks up the hidden counter‑factual outcome for that (event_id, action) and returns execution result (success, recovered_amount, etc.).
6. **Verifier** returns the executor result as verification.
7. Metrics are aggregated: total recovered revenue, recovery rate, attempts, contacts, cost, etc.
8. Baseline vs RevenueOS compared.

## Current Model Flow

- Training: `backend/app/ml/training.py` loads synthetic data, engineers features (amount, hour, day, is_weekend, historical_success_rate, avg_transaction_value, avg_ticket_size, one‑hot payment method, failure reason, failure pattern, merchant plan), trains LogisticRegression on label `would_recover_with_action_B`, saves model and feature names.
- Inference: `backend/app/recoverability_model.py` loads model & feature names, extracts features for a given event (joining payment, customer, merchant), calls `model.predict_proba` → returns probability of recovery for action B. For other actions it falls back to a heuristic based on failure reason and amount.
- The model does **not** take action as a feature; it is action‑specific (only for action B) plus heuristic fallback.

## Current Experiment Flow (Runner)

1. `backend/app/experimentation/runner.py`:
   - Loads held‑out test events.
   - Instantiates Baseline strategy and RevenueOS strategy (greedy EV).
   - For each event:
        - Build DecisionContext.
        - Get action from each strategy.
        - Apply policy engine (already yields approval status).
        - If approved, call execution layer → simulator → get outcome.
        - Record outcomes.
   - After loop, compute metrics using `backend/app/experimentation/metrics.py`.
   - Generate report via `backend/app/experimentation/reports.py`.
   - Save JSON report under `data/experiments/`.

## Weaknesses Discovered

1. **Model is not action‑aware**: Only PAYMENT_LINK has a learned probability; other actions use heuristics that may not generalize.
2. **Utility function is missing**: RevenueOS strategy currently maximizes `expected_recovered = amount * P(recovery)` without subtracting action cost, friction, retry/contact penalties, or time delay.
3. **Policy engine not fully integrated**: The strategy selects an action before checking policy; the policy engine can block, but the strategy does not consider policy constraints in its scoring (could select a blocked action then waste effort). Should integrate policy into utility (e.g., set utility to -inf for blocked actions).
4. **No action‑specific cost/friction modeling**: All actions assumed same cost except where hard‑coded in heuristic.
5. **No cascading / multi‑step decision making**: The strategy picks one action per event; real recovery may involve sequences (e.g., notification → payment link). Not required for Phase 2B but could be considered.
6. **Audit trail not fully populated**: `audit_events` table exists but is not yet used to store decisions, policy checks, executions, verifications.
7. **Model evaluation limited**: Only accuracy/precision/recall/F1/ROC‑AUC reported on validation; no calibration, Brier score, PR‑AUC, or ranking‑based metrics.
8. **No ablation study** to determine which components (probability, cost, friction, policy) drive any observed uplift.
9. **Single‑seed experiment only**: Results may vary with random seed; need multiple seeds to show robustness.
10. **Feature leakage risk**: While we built `DecisionContext` to hide ground truth, we must ensure the model does not inadvertently see future columns (e.g., via derived features like avg_transaction_value that could be correlated with outcome). Need explicit tests.

## Risks to Scientific Validity & Mitigations

| Risk | Mitigation |
|------|------------|
| Data leakage via features (e.g., using future‑derived stats) | Build explicit `DecisionContext` class that only exposes allowed columns; write automated leakage test that attempts to train a model using hidden columns and verifies performance drops to chance. |
| Overfitting to validation set when choosing model | Use validation set only for model selection; keep held‑out test completely untouched until final experiment. Report validation performance but final numbers only from test set. |
| Tuning utility weights to improve test result | Keep utility weights configurable but set them a priori (e.g., based on business reasoning: action cost = ₹1 per retry, friction penalty = ₹10 per contact, delay penalty = ₹0.1 per hour, etc.) and justify in docs. Do not tune weights on test set. |
| Single‑seed fluke | Run multiple seeds and report central tendency and spread. |
| Mistakenly counting unrecovered revenue as recovered | Verification step only counts revenue when simulator outcome indicates success (recovered_amount > 0). Ensure NO_ACTION and failed actions yield zero recovered. |
| Policy engine being bypassed | Strategy queries policy engine before computing utility; if policy returns BLOCKED or REQUIRES_HUMAN_APPROVAL (and we are not simulating human approval), treat as not permitted (utility = -∞). |
| Auditor viewing PII in audit trail | Store only IDs, counts, Booleans; no raw names, emails, etc. |
| Non‑deterministic simulator due to randomness | Simulator is a pure lookup table; no random numbers after data generation. Ensure any UUID generation for action_id does not affect outcome (we store results in a dict keyed by a deterministic key like (event_id, action, timestamp? but we keep timestamp as part of context; we can use a hash of context+action as idempotency key). |
